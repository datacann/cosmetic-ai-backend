# Cosmetic AI database

## Local setup

1. Start PostgreSQL:

   `docker compose up -d postgres`

2. Copy `DATABASE_URL` from `.env.example` into `.env`.

3. Apply schema migrations:

   `.venv\Scripts\alembic.exe upgrade head`

4. Start the API normally.

When `DATABASE_URL` is absent, persistence and database cache are disabled and the
existing analysis flow continues unchanged. When it is present, a successful full
analysis stores the catalog, formula version, ingredient order, profile snapshot,
and scoring result. A later exact product match can reuse a complete saved formula.

## Authentication and profiles

Set `AUTH_SECRET_KEY` to a random value of at least 32 characters. The local setup
loads it from the git-ignored `.env.auth` file. Production must use a secret manager
and a different value.

- `POST /v1/auth/register`: create an account and receive a 30-minute access token.
- `POST /v1/auth/token`: log in with OAuth2 form fields (`username` is the email).
- `GET /v1/users/me`: read the authenticated account.
- `GET/PUT /v1/users/me/profile`: read or update the saved skin profile.
- `GET /v1/users/me/analyses`: list the authenticated user's analysis history.

Passwords are stored only as Argon2 hashes. JWTs are signed, not encrypted, so no
password, profile, or other private information is placed in their payload. Full
analysis remains available anonymously; with a Bearer token it is linked to the
user, and a saved profile may replace the `skin_profile` form field.

## Migration workflow

After changing SQLAlchemy models:

1. Generate: `.venv\Scripts\alembic.exe revision --autogenerate -m "change summary"`
2. Review the generated upgrade and downgrade functions.
3. Apply: `.venv\Scripts\alembic.exe upgrade head`
4. Verify: `.venv\Scripts\alembic.exe check`

Never treat an autogenerated migration as automatically correct; it is a candidate
that must be reviewed before deployment.
